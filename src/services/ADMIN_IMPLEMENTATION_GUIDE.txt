================================================================================
ADMIN WEB APP IMPLEMENTATION GUIDE
DataCapturing & Measurement Platform
Target: Next.js Web Application (Exact Replica of React Native Admin)
================================================================================

BASE URL: https://backend-data-capturing-and-measurement.onrender.com/api

AUTHENTICATION:
  - All protected endpoints require: Authorization: Bearer <token>
  - Token storage key: "userToken" (AsyncStorage / localStorage / cookie)
  - Token is a JWT; decode to read: role, organizationId, userId, exp
  - On 401/403: redirect to /login

ROLE-BASED API PATH ROUTING:
  - ORGANIZATION role     --> use /admin/* endpoints
  - CUSTOMER + organizationId --> use /org-user/* endpoints
  - Regular CUSTOMER      --> use /user/* endpoints
  - SUPER_ADMIN           --> use /super-admin/* endpoints

CURRENCY: Nigerian Naira (NGN). Always display with symbol: ₦
  - Use the "actualAmount" field (NOT "priceInDollars") for all price display.
  - Format: amount.toLocaleString() with ₦ prefix.

IMAGE URL FALLBACK CHAIN (in order):
  item.imageUrl || item.image || item.picture || item.photo

SECTION 1: AUTHENTICATION SCREENS
================================================================================

--------------------------------------------------------------------------------
SCREEN: LoginScreen
ROUTE: /login
--------------------------------------------------------------------------------
PURPOSE: Email/password login with role-based post-login routing.

UI ELEMENTS:
  - Email input (keyboard type: email-address, auto-lowercase)
  - Password input (secureTextEntry toggle with eye icon)
  - "Login" button (purple #7C3AED, disabled + spinner during loading)
  - "Forgot Password?" link --> /forgot-password
  - "Sign Up" link --> /signup

API CALLS:
  POST /auth/login
  Body: { email: email.toLowerCase(), password }
  Response: { jwtToken, user: { role, isVerified, organizationId, _id } }

BUSINESS LOGIC:
  1. If response.data.user.isVerified === false:
     - Navigate to /verify-otp with params: { email, fromLogin: true }
  2. Store jwtToken in localStorage (key: "userToken")
  3. Role-based routing after storing token:
     a. SUPER_ADMIN --> /super-admin/dashboard
     b. ORGANIZATION role:
        - Call GET /user-subscriptions/user/:userId/status
        - If hasActiveSubscription === true --> /admin/dashboard
        - Else --> /subscription-selection
     c. CUSTOMER with organizationId --> /admin/dashboard (org user area)
     d. Regular CUSTOMER --> /user/dashboard

ERROR HANDLING:
  - error.message includes "EMAIL_NOT_VERIFIED" --> redirect to /verify-otp
  - error.message includes "ACCOUNT_SUSPENDED" --> show alert "Account Suspended"
  - Generic errors: show error.message in red below form

--------------------------------------------------------------------------------
SCREEN: ForgotPasswordScreen
ROUTE: /forgot-password
--------------------------------------------------------------------------------
PURPOSE: Enter email to receive OTP for password reset.

UI ELEMENTS:
  - Email input
  - "Send Reset Code" button
  - 60-second resend countdown timer (shown after first send)
  - "Resend Code" button (disabled during countdown)
  - Back link to /login

API CALLS:
  POST /auth/forgot-password
  Body: { email: email.toLowerCase() }
  Response: { message, otpData }

BUSINESS LOGIC:
  - On success: navigate to /reset-password with params: { email, otpData }
  - Start 60-second countdown; "Resend Code" button disabled until 0
  - Detect rate limiting: if response.message includes "Please wait" --> show wait message
  - After countdown reaches 0, allow resend

--------------------------------------------------------------------------------
SCREEN: ResetPasswordScreen
ROUTE: /reset-password
--------------------------------------------------------------------------------
PURPOSE: Enter 6-digit OTP received via email.
(This is the OTP entry step between ForgotPassword and SetNewPassword)

PARAMS: { email, otpData }

UI ELEMENTS:
  - 6 individual digit input boxes (auto-advance on input, auto-backspace on delete)
  - Countdown timer displaying time remaining
  - "Verify OTP" button
  - "Resend OTP" button (active after countdown expires)

API CALLS:
  POST /auth/verify-otp
  Body: { email, otp: sixDigitString }

  POST /auth/resend-otp (for resend)
  Body: { email }

BUSINESS LOGIC:
  - otpData.remainingAttempts: show attempts remaining
  - otpData.maxAttempts: total allowed attempts
  - otpData.otpExpiresIn: set countdown (seconds); fallback to 600 if null
  - On success: navigate to /set-new-password with params: { email, otp }
  - On expiry: show "OTP expired. Please request a new one."
  - Each box: maxLength 1, numeric only

--------------------------------------------------------------------------------
SCREEN: SetNewPasswordScreen
ROUTE: /set-new-password
--------------------------------------------------------------------------------
PURPOSE: Final step of password reset. Enter and confirm new password.

PARAMS: { email, otp }

UI ELEMENTS:
  - New Password input (secureTextEntry toggle)
  - Confirm Password input (secureTextEntry toggle)
  - "Set New Password" button

API CALLS:
  POST /auth/reset-password
  Body: { email: email.toLowerCase(), otp, newPassword }

VALIDATION:
  - Minimum 6 characters
  - Passwords must match
  - Show inline error if validation fails

BUSINESS LOGIC:
  - On success: navigate to /login (replace history)
  - Show success message before redirect

--------------------------------------------------------------------------------
SCREEN: VerifyOTPScreen
ROUTE: /verify-otp
--------------------------------------------------------------------------------
PURPOSE: Email verification for new accounts.

PARAMS: { email, otpData, fromLogin }

UI ELEMENTS:
  - 6 individual digit input boxes
  - Timer countdown (format: MM:SS)
  - "Verify Account" button
  - "Resend OTP" button

API CALLS:
  POST /auth/verify-otp
  Body: { email, otp }

  POST /auth/resend-otp
  Body: { email }

BUSINESS LOGIC:
  - If fromLogin === true AND no otpData: auto-call resendOTP() on mount
  - otpData.otpExpiresIn sets initial countdown (fallback: 600 seconds)
  - On success: navigate to /login (replace history; do NOT store token or go to dashboard)
  - On expired OTP: allow resend

ROUTE: /admin/users
--------------------------------------------------------------------------------
PURPOSE: List, search, filter, and manage organization users.

API CALLS:
  GET /{baseUrl}/users?page={page}&limit=10&includeOrganization=true
  Response: {
    users: [{ _id, id, fullName, email, customUserId, role, status, organizationId, roleId, createdAt }],
    pagination: { totalPages, total, hasNextPage, hasPrevPage }
  }

  POST /{baseUrl}/users (create user)
  Body: { firstName, lastName, email, phoneNumber, role (optional), password (optional), generateNew: bool }

UI ELEMENTS:
  - Search bar (client-side filter on fullName, email, customUserId)
  - Status filter tabs: All | Active | Pending | Archived
  - Paginated user list (10 per page)
  - Each card: fullName, email, customUserId, status badge, role
  - "Create User" FAB / button
  - Create User inline modal:
    * firstName, lastName, email, phoneNumber (required)
    * Role dropdown (optional)
    * generatePassword toggle (Switch)
    * If generatePassword off: password input (required)
  - Load More / pagination controls

BUSINESS LOGIC:
  - Status filtering: client-side after fetch (not query param)
  - Before creating: check ModuleAccessChecker.checkUsageLimit('orgUsers')
    * GET /user-subscriptions/check-usage-limit/orgUsers
    * If limit reached: show upgrade prompt, abort creation
  - On create success:
    * If response.data.generatedPassword: store in localStorage key "userPasswords"
      as JSON { [userId]: password, [customUserId]: password }
    * Show generated password to admin in success modal
  - Navigate to user details: fetch GET /{baseUrl}/users/:userId first, then navigate with full user object

STATUS BADGE COLORS:
  - active: #10B981 (green)
  - pending: #F59E0B (yellow)
  - archived: #6B7280 (gray)

PURPOSE: Full detail view of an org user with management actions.

API CALLS:
  GET /{baseUrl}/users/:userId (fresh fetch on mount)
  Response: { user: { ...fields } }

  GET /{baseUrl}/users/:userId/measurements?page=1&limit=20
  Response: { measurements: [...] }

  PUT /{baseUrl}/users/:userId (edit)
  Body: { firstName, lastName, email, phoneNumber, role? }

  PUT /{baseUrl}/users/:userId/status
  Body: { status: 'active'|'pending'|'archived' }

  PUT /{baseUrl}/users/:userId/password
  Body: { password: newPassword }

  POST /{baseUrl}/users/:userId/send-email
  Body: { adminMessage, generateNewPassword: true }

UI ELEMENTS:
  - User info card: fullName, email, customUserId, status badge, role
  - Password display (retrieved from localStorage "userPasswords" keyed by userId or customUserId)

    * active user: "Archive" button, "Set Pending" button
    * pending user: "Activate" button, "Archive" button
    * archived user: "Activate" button
  - Action buttons: "Reset Password" | "Edit User" | "Send Email" | "View Permissions"
  - Measurements list (paginated, 20 per page)
    * hasMore: true if returned count === 20
    * Each measurement tappable --> /admin/measurements/:id

  - Modals:
    * Reset Password: new password input, confirm, submit
    * Edit User: firstName, lastName, email, phoneNumber, role
    * Send Email: adminMessage textarea (generateNewPassword always true)

STATUS TRANSITION RULES:
  active --> pending (Set Pending button)
  active --> archived (Archive button)
  pending --> active (Activate button)
  pending --> archived (Archive button)
  archived --> active (Activate button)

BUSINESS LOGIC:
  - Password: read from localStorage "userPasswords"[user.id || user.customUserId]
  - Navigate to MeasurementDetails: /admin/measurements/:measurementId
  - Navigate to UserPermissions: /admin/users/:userId/permissions

SECTION 9: ADMIN BOOKING FLOW (5-STEP)
================================================================================

The admin booking flow allows organization admins to book services on behalf of customers.
Flow: SelectDay --> SelectTime --> EnterDetails --> SelectLocation --> ConfirmSchedule

--------------------------------------------------------------------------------
SCREEN: AdminBookingStep1SelectDayScreen
ROUTE: /admin/booking/step1
--------------------------------------------------------------------------------
PURPOSE: Select available booking day from calendar.

PARAMS: { service } (gallery item object)

API CALLS:
  GET /admin/booking/available-days?month={month}&year={year}&serviceId={serviceId}
  Response: { availableDays: ['2024-01-15', '2024-01-16', ...] }

UI ELEMENTS:
  - Month/year header with prev/next navigation arrows
  - 6-week calendar grid (Sun-Sat)
  - Available days: highlighted/clickable (purple)
  - Unavailable days: grayed out
  - Selected day: filled purple circle
  - "Next" button (disabled until day selected)

BUSINESS LOGIC:
  - Calendar starts from Sunday of the week containing the 1st of the month
  - On month change: re-fetch available days for new month/year
  - On "Next": navigate to Step 2 with { service, selectedDate }

--------------------------------------------------------------------------------
SCREEN: AdminBookingStep2SelectTimeScreen
ROUTE: /admin/booking/step2
--------------------------------------------------------------------------------
PURPOSE: Select available time slot for chosen date.

PARAMS: { service, selectedDate }

API CALLS:
  GET /admin/booking/available-slots?date={selectedDate}&serviceId={serviceId}
  Response: { slots: [{ datetime, startTime, endTime, available, providerCount }] }

UI ELEMENTS:
  - Selected date display (formatted: "Monday, January 15, 2024")
  - Time slot grid (FlatList)
  - Each slot: startTime - endTime, duration (from service.bookingAvailability.slotDurationMinutes, fallback 60 min)
  - Selected slot: purple border/fill
  - "Next" button (disabled until slot selected)
  - Back button

BUSINESS LOGIC:
  - slot selected by: selectedSlot?.datetime === slot.datetime
  - On "Next": navigate to Step 3 with { service, selectedDate, selectedSlot }

--------------------------------------------------------------------------------
SCREEN: AdminBookingStep3EnterDetailsScreen
ROUTE: /admin/booking/step3
--------------------------------------------------------------------------------
PURPOSE: Select customer and service provider, enter booking details.

PARAMS: { service, selectedDate, selectedSlot }

API CALLS:
  GET /admin/booking/organization-users?search={search}&page=1&limit=20
  Response: { users: [{ id, _id, fullName, email, phoneNumber, customUserId }] }

  GET /service-provider-assignment/detailed
  Response: { serviceProviders: [{ id, fullName, email, specialties, isActive }] }

UI ELEMENTS:
  - Customer type toggle: "Existing Customer" | "External Customer"
  - If "Existing": searchable user list (from org users)
  - If "External": Name input, Email input, Phone input
  - Service Provider selector (from org's assigned providers)
  - Customer Notes textarea
  - Number of guests (optional)
  - "Next" button

STATE:
  customerType: 'existing' | 'external'
  selectedCustomer: user object (if existing)
  externalCustomer: { name, email, phone }
  selectedProvider: provider object
  serviceProviders: []
  orgUsers: []
  customerNotes: ''
  guests: 0

BUSINESS LOGIC:
  - On "Next": navigate to Step 4 with { service, selectedDate, selectedSlot, bookingDetails }
  - bookingDetails object: { customerType, customer (existing object or external data), selectedProvider, customerNotes, guests }

--------------------------------------------------------------------------------
SCREEN: AdminBookingStep4SelectLocationScreen
ROUTE: /admin/booking/step4
--------------------------------------------------------------------------------
PURPOSE: Select service delivery location type.

PARAMS: { service, selectedDate, selectedSlot, bookingDetails }

API CALLS:
  GET /admin/booking/location-options?serviceId={serviceId}
  Response: { locationOptions: { merchant_location: {...}, customer_address: {...}, ... }, defaultOption, organizationName }

  POST /admin/booking/validate-location
  Body: { locationType, address, whatsappLocationUrl, customerEmail }

UI ELEMENTS:
  - Location type radio buttons (from locationOptions keys):
    * merchant_location: "Our Location" (default)
    * customer_address: "Customer's Address"
    * whatsapp_location: "WhatsApp Location"
  - If customer_address: custom address text input
  - If whatsapp_location: WhatsApp location URL input
  - Organization name display for merchant_location
  - "Next" button

BUSINESS LOGIC:
  - defaultOption from API response sets initial selection
  - Validate location on "Next" before proceeding
  - On validation success: navigate to Step 5 with { ..., locationData: validatedLocationData }

--------------------------------------------------------------------------------
SCREEN: AdminBookingStep5ConfirmScheduleScreen
ROUTE: /admin/booking/step5
--------------------------------------------------------------------------------
PURPOSE: Review summary, select sub-services, calculate pricing, create booking.

PARAMS: { service, selectedDate, selectedSlot, bookingDetails, locationData }

API CALLS:
  GET /admin/booking/services/:serviceId/sub-services
  Response: { subServices: { subServices: [...] } } (note: nested)
  Each subService: { _id, name, price, description, subPlatformUniqueCode }

  POST /admin/booking/calculate-pricing
  Body: {
    serviceId,
    bookedForPersons: [{ name: customerName, selectedSubServices: [subServiceId, ...] }],
    paymentType: 'upfront' | 'full',
    upfrontPercentage: number (if paymentType === 'upfront')
  }
  Response: { pricing: { totalFee, upfrontFee, remainingFee, breakdowns: [...] } }

  POST /admin/booking/create
  Body: {
    serviceId,
    slotDateTime: selectedSlot.datetime,
    customerType,
    customerId (if existing customer),
    externalCustomer (if external),
    serviceProviderId,
    locationData,
    selectedSubServices: [subServiceId, ...],
    paymentType: 'upfront'|'full',
    processPayment: bool,
    customerNotes,
    guests
  }
  Response: { booking: { bookingId, taskId, slotDateTime, paymentLink, transactionId, serviceName } }

UI ELEMENTS:
  - Booking summary card: service name, date/time, customer name, provider, location
  - Sub-services selection (checkboxes)
  - Payment Type toggle: "Full Payment" | "Upfront Payment"
  - If Upfront: show upfrontPaymentPercentage and upfrontPaymentAmount from service details
  - Pricing breakdown card (shown after calculate-pricing API response):
    * Total Fee, Upfront Fee, Remaining Fee
  - Process Payment toggle (Switch, default: true)
  - "Confirm Booking" button

BUSINESS LOGIC:
  - Sub-services path: response.data.subServices?.subServices || response.data.subServices
  - upfrontPaymentPercentage: from service.upfrontPaymentPercentage field
  - On "Confirm Booking":
    * If processPayment === true AND response.booking.paymentLink:
      --> navigate to AdminBookingPayment with { booking, paymentLink }
    * Else: navigate to AdminBookingSuccess with { booking }

--------------------------------------------------------------------------------
SCREEN: AdminBookingPaymentScreen
ROUTE: /admin/booking/payment
--------------------------------------------------------------------------------
PURPOSE: Payment processing for admin booking via Flutterwave WebView.

PARAMS: { booking, paymentLink }

API CALLS:
  POST /orders/public/verify
  Body: { transactionId: booking.transactionId || booking.tx_ref }

UI ELEMENTS:
  - WebView displaying paymentLink
  - "Verify Payment" button (manual verification)
  - 3-minute timeout alert: offers manual verification

BUSINESS LOGIC:
  - Auto-verify after 3 minutes (timeout) with confirm dialog
  - On payment verified: navigate to AdminBookingSuccess
  - transactionId: booking.transactionId || booking.tx_ref

POST   /auth/resend-otp                         Resend OTP
POST   /auth/forgot-password                    Request password reset
POST   /auth/reset-password                     Reset password with OTP

--- ROLE-BASED USERS (path prefix varies by role) ---
GET    /{prefix}/users                          List users (page, limit, includeOrganization)
GET    /{prefix}/users/:id                      Get user by ID
POST   /{prefix}/users                          Create user
PUT    /{prefix}/users/:id                      Update user
PUT    /{prefix}/users/:id/status               Update user status
PUT    /{prefix}/users/:id/password             Reset user password
POST   /{prefix}/users/:id/send-email           Send email to user
GET    /{prefix}/users/:id/measurements         Get user measurements

--- ROLE-BASED MEASUREMENTS ---
GET    /{prefix}/measurements                   List measurements (page, limit, userId)
GET    /{prefix}/measurements/:id               Get measurement
POST   /{prefix}/measurements                   Create measurement
PUT    /{prefix}/measurements/:id               Update measurement
DELETE /{prefix}/measurements/:id               Delete measurement

--- ROLE-BASED ROLES ---
GET    /{prefix}/roles                          List roles (page, limit, includeUsers)
GET    /{prefix}/roles/:id                      Get role (includeUsers)
POST   /{prefix}/roles                          Create role
PUT    /{prefix}/roles/:id                      Update role
DELETE /{prefix}/roles/:id                      Delete role
POST   /admin/roles/:id/assign                  Assign role to users (body: {userIds})

--- ROLE-BASED GROUPS ---
GET    /{prefix}/groups                         List groups
GET    /{prefix}/groups/:id                     Get group
POST   /{prefix}/groups                         Create group
PUT    /{prefix}/groups/:id                     Update group
PUT    /{prefix}/groups/:id/members             Add/remove members (body: {action, userIds})
DELETE /{prefix}/groups/:id                     Delete group

--- ROLE-BASED ONE-TIME CODES ---
GET    /{prefix}/one-time-codes                 List codes (page, limit)
POST   /{prefix}/one-time-codes                 Generate code
POST   /{prefix}/one-time-codes/send-email      Send code via email

--- ROLE-BASED PERMISSIONS ---
GET    /{prefix}/permissions                    Get permissions
GET    /{prefix}/user-permissions               Get available permissions list
GET    /admin/users/:id/permissions             Get user permissions (super admin)
PUT    /admin/users/:id/permissions             Update user permissions (super admin)

--- DASHBOARD ---

SECTION 19: KEY PATTERNS & GOTCHAS
================================================================================

1. ROLE-BASED API PREFIX
   Every API call in the service file resolves the prefix dynamically:
   - ORGANIZATION --> /admin
   - CUSTOMER + organizationId --> /org-user
   - regular CUSTOMER --> /user
   DO NOT hardcode /admin/ for all calls. Check user.role + user.organizationId each time.

2. CURRENCY: ALWAYS USE actualAmount
   - item.actualAmount is the final price in NGN (Nigerian Naira)
   - item.priceInDollars is the base price before platform charges
   - Display format: ₦{actualAmount.toLocaleString()}
   - NEVER display priceInDollars to end users

3. IMAGE FALLBACK CHAIN
   const imageUrl = item.imageUrl || item.image || item.picture || item.photo
   Always use this fallback. Different item types use different field names.

4. GALLERY ITEMS: id vs _id
   - GalleryManagementScreen uses item._id for API calls (POST /admin/gallery/:id)
   - AdminGalleryItemsScreen uses item.id (not ._id) for navigation
   - Be aware: both may exist; prefer the one the API returns for that endpoint

5. PAGINATION PATTERN
   Response: { items: [...], pagination: { totalPages, total, hasNextPage, hasPrevPage } }
   Or: { items: [...], totalPages, total, totalOrders }
   Or simple hasMore: returned.length === limit (20 or 10)
   Always check response structure before rendering pagination.

6. SUBSCRIPTION MODULE ACCESS CHECK
   Before creating users or measurements:
   GET /user-subscriptions/check-usage-limit/orgUsers  (for users)
   GET /user-subscriptions/check-usage-limit/bodyMeasurements  (for measurements)
   If limit reached: show upgrade modal, do NOT proceed with creation.
   ModuleAccessChecker.checkUsageLimit(type) wraps this call.

7. PASSWORD STORAGE PATTERN
   When an org user is created:
   - Backend returns generatedPassword in response
   - Store in localStorage key "userPasswords" as JSON: { [userId]: password }
   - Also key by customUserId: { [customUserId]: password }
   - When viewing UserDetails, read from this storage to show to admin
   - This is NOT stored on the server; it's purely a client-side convenience feature

8. LOGIN FLOW: ORGANIZATION SUBSCRIPTION CHECK
   After storing token for ORGANIZATION role:
   1. GET /user-subscriptions/user/:userId/status
   2. If response.data.hasActiveSubscription === true: go to AdminDashboard
   3. Else: go to SubscriptionSelection page
   Don't skip this check or the org may land on dashboard without a valid subscription.

9. OTP VERIFICATION (VerifyOTPScreen)
   - IMPORTANT: On success, navigate to LOGIN (not dashboard)
   - Do NOT store token from verify-otp response
   - Do NOT navigate to dashboard from this screen
   - The user must log in again after verifying their email

10. SEND EMAIL: generateNewPassword ALWAYS TRUE
    AdminBookingSuccessScreen and UserDetailsScreen send emails with:
    { adminMessage: "...", generateNewPassword: true }
    The generateNewPassword field is ALWAYS hardcoded to true when sending.

11. SUPER ADMIN PROFILE MERGE
    GET /auth/profile for SUPER_ADMIN role:
    - The service auto-calls GET /super-admin/profile additionally
    - Merges displayName, fullName, firstName, lastName from super admin profile
    - This ensures the correct name is shown for super admins

12. ADMIN DASHBOARD NOTIFICATION BADGE
    GET /admin/notifications/unread-count
    Returns: { unreadCount: number }
    Show as badge on notification bell icon. Refresh on screen focus.

13. BOOKING STEP 5: SUB-SERVICES NESTED RESPONSE
    GET /admin/booking/services/:id/sub-services
    Response structure: response.data.subServices?.subServices || response.data.subServices
    (Note the double nesting - always check both paths)

14. LOCATION OPTIONS RESPONSE
    GET /admin/booking/location-options
    Returns: { locationOptions: { merchant_location: {...}, customer_address: {...} }, defaultOption, organizationName }
    Set initial selectedLocationType = response.data.defaultOption || 'merchant_location'

15. ORGANIZATION PROFILE: LOCATION CHECK ON DASHBOARD
    When clicking "Organization Profile" quick action:
    - First call GET /admin/organization-profile
    - Check: response.data?.profile?.locations?.length > 0
    - If yes: go to OrganizationLocations
    - If no/empty: go to OrganizationProfileSetup

16. BOTTOM NAVIGATION: ORGANIZATION ONLY
    The BottomNavigation component on AdminDashboard is shown ONLY for role === 'ORGANIZATION'
    CUSTOMER users with organizationId do NOT see the bottom nav.

17. USER STATUS TRANSITIONS
    Valid transitions:
    active --> archived (via Archive action)
    active --> pending (via Set Pending action)
    pending --> active (via Activate action)
    pending --> archived (via Archive action)
    archived --> active (via Activate action)
    No transition: active <--> archived directly bypasses pending in some flows; check UI.

18. CREATE GROUP: MEMBER MANAGEMENT
    Initial create: send memberIds in POST body
    Edit members after creation: use PUT /groups/:id/members with { action: 'add'|'remove', userIds: [...] }

19. MEASUREMENT UNIT PROPAGATION
    In AdminCreateMeasurementScreen:
    - All sections share ONE measurement unit
    - Unit is set on section 1 and propagates to all sections
    - Trying to change unit on section 2+ is blocked with an alert
    - Only the first section's unit dropdown is functional

20. PAYMENT FLOW: PAYMENTTYPE IN LOCALSTORAGE
    When initializing different payment types, the app stores "paymentType" in AsyncStorage:
    - subscription payment: stores "subscription"
    - combined payment (sub + badge): stores "combined"
    - verified badge only: stores "verified-badge"
    On verify: reads paymentType, routes to correct verify endpoint.
    Clears paymentType after successful verification.

21. MULTIPART/FORM-DATA UPLOADS
    For gallery creation, verification submission, task completion:
    - Do NOT set Content-Type header manually
    - Let browser/fetch set it automatically with the correct boundary
    - Otherwise multipart parsing will fail on the server

22. SUPER ADMIN: MANDATORY ROLE CHECK ON EVERY SCREEN
    Every super admin screen calls GET /auth/profile on mount
    Checks: response.data.user.role !== 'SUPER_ADMIN'
    If check fails: show Alert, navigation.goBack()
    Replicate this guard on every super admin route in Next.js middleware or layout.

23. DATE FORMAT CONVENTIONS
    Standard display: new Date(dateString).toLocaleDateString('en-US', { year:'numeric', month:'long', day:'numeric' })
    With time: add hour:'2-digit', minute:'2-digit'
    Short format: month:'short', day:'numeric', year:'numeric'
    All dates from API are ISO strings.

24. TIME AGO FORMULA
    diff = (Date.now() - new Date(iso)) / 1000
    < 60: "{floor(diff)}s ago"
    < 3600: "{floor(diff/60)}m ago"
    < 86400: "{floor(diff/3600)}h ago"
    >= 86400: "{floor(diff/86400)}d ago"

25. ADMIN BOOKING SOURCE DETECTION
    booking.bookedByAdmin === true --> show "Admin Booked" badge (purple)
    booking.bookingSource field (if available)
    Fallback: presence of userId field

26. SETTLEMENT AMOUNT CALCULATION
    Total amount on AdminSettlementsManagementScreen is calculated CLIENT-SIDE:
    settlements.reduce((sum, s) => sum + (s.amount || 0), 0)
    NOT returned by the API as a pre-computed total.

27. MEASUREMENTS HASMORE PATTERN (simple pagination)
    In UserDetailsScreen for user measurements:
    hasMore = (returned measurements count === 20)
    Page increments by 1 on "Load More"
    Not based on pagination object, just count === limit

28. VERIFIED BADGE PAYMENT FLOW
    Three separate payment flows are stored differently:
    a. Subscription only: POST /payment/initialize --> POST /payment/verify
    b. Verified badge only: POST /payment/verified-badge/initialize --> POST /payment/verified-badge/verify
    c. Combined (sub + badge): POST /payment/combined/initialize --> POST /payment/combined/verify
    Check stored "paymentType" value to route verification correctly.

29. ADMIN GALLERY vs ORGANIZATION GALLERY
    /admin/gallery --> organization's OWN items (they created/uploaded)
    /admin/gallery/items --> ALL platform items from all organizations
    These are different endpoints with different data scopes.

30. SUPER ADMIN ANALYTICS FALLBACKS
    Analytics screen uses || '0%' and || '0' fallbacks for all values:
    analytics.userGrowth || '0%'
    analytics.activeSessions || '0'
    Always provide fallback since analytics endpoint may return partial data.
